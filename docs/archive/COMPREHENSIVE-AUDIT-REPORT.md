# التقرير الشامل النهائي لتدقيق مشروع AI AYFAM

**تاريخ الدمج:** 2026-10-12  
**النطاق:** دمج نتائج مراجعات Python/المحركات/الأمن/واجهة Angular/API/التثبيت والاختبارات.  
**حالة التعديلات:** أُغلقت مجموعة العوائق المؤكدة والنتائج العالية القابلة للإصلاح في commit لاحق، مع إبقاء النتائج التي تحتاج إعادة تصميم أوسع ضمن المخاطر المتبقية.

> **منهجية الدمج:** هذا تقرير توحيد وترتيب، وليس فحصاً جديداً من الصفر. أزيلت النتائج المتكررة بين المراجعين وربطت كل نتيجة بمصدرها البرمجي الحالي. تحقّق موضعي من الملفات الحالية أكّد، ضمن أمور أخرى، عدم تطابق واجهات `main.py` مع أساليب الوكيل، ووجود `eval` في مولّد المعالجة، وغياب `pypdf` من المتطلبات، وربط Angular على `0.0.0.0`، ومسار `shell=True` في الواجهة الرسومية. لم تُشغّل مجموعة الاختبارات أو المثبّت لأن المطلوب كان دمج المراجعات لا إعادة التدقيق.

## الملخص التنفيذي

المشروع لديه أساسات دفاعية جيدة — مثل `safe_exec` بقوائم argv و`shell=False` في أغلب المسارات، وإخفاء الأسرار في العرض، وتأكيدات تفاعلية قبل بعض الأفعال المؤثرة، وtimeouts للاتصالات المعتادة — لكنه **غير جاهز للتشغيل الإداري أو النشر كأداة أمنية موثوقة** قبل معالجة النتائج الحاجبة والعالية.

أهم المشكلات العملية هي:

1. **واجهة CLI غير قابلة للعمل في أوضاعها الفعلية:** تستدعي `main.py` أساليب غير موجودة، و`--check` يعامل `PreflightReport` كقاموس.
2. **خطر تنفيذ أوامر من بيانات نتائج الفحص:** مولّد خطة المعالجة يضمّن نص `fix` في Bash ثم ينفذه بـ`eval`. كما أن واجهة GUI تملك مساراً مستقلاً يستدعي `subprocess.run(..., shell=True)` لنص إصلاح من finding.
3. **التثبيت النظيف واختباراته غير موثوقين:** يستورد `setup.sh` مكتبة `pypdf` غير الموجودة في `requirements.txt`، ولا تُعلن `pytest` ضمن متطلبات الاختبار. معظم ملفات الاختبار لا تفرض فشلاً على المشغّل وفق نتائج المراجعة.
4. **مسار واجهة الويب يعرّض proxy غير موثّق:** `npm run start/dev` يربط على كل الواجهات ويحوّل `/api` إلى خادم محلي يستخدم مفاتيح مزودين سحابيين بلا مصادقة أو rate limit.
5. **فجوات كشف وتكامل تؤثر في سلامة القرار الأمني:** تشمل فحص أذونات الحسابات، مفاتيح خاصة، أوامر `authorized_keys`، ترتيب سجلات SSH/IPv6، وربط SUID، إضافة إلى ادعاءات نجاح محلية في واجهة SOC لا تمثل تنفيذ backend.

**قرار الإصدار المقترح:** لا تُصدر كأداة ذات امتيازات ولا تنشر واجهة Angular خارج loopback حتى إغلاق نتائج الخصوصية وSSRF والاختبارات الحية المتبقية. خطة المعالجة المولدة أصبحت مراجعة غير تنفيذية، ومسار GUI لم يعد ينفذ نصوص finding الحرة.

## الإصلاحات المنفذة في هذه الجولة

- إصلاح عقد CLI وإضافة `interactive_loop` و`run_full_audit` و`run_hardening` و`search_cve`، وتصحيح `--check` ليعرض `PreflightReport` ويعيد رمز خروج مناسب.
- إزالة التنفيذ الديناميكي من مولّد خطط المعالجة؛ الناتج الآن قائمة مراجعة فقط.
- إزالة `shell=True` من زر إصلاح GUI وقصر التطبيق على `fix_id` مسجل ومتحقق.
- تقوية صلاحيات ملفات الحسابات لكشف الكتابة الجماعية، وتوسيع ماسح الأسرار إلى `id_rsa` و`id_ed25519` و`.pem` و`.key`.
- إضافة `pypdf` و`pytest` إلى المتطلبات، وتحسين غلاف HTTP لدعم `stream` و`json` و`data`.
- حفظ إعدادات ذري مع `fsync` و`os.replace` ومنع symlink المباشر.
- تقوية API المحلي بتحقق JSON وContent-Length وsocket timeout، وجعل Angular loopback افتراضياً.

| **medium** | تشغيل إداري ووثائق — `setup.sh`, `README.md`, `INSTALL.md`, `ayfam-gui-launcher.sh` | launchers مملوكة root تشير لشجرة قد يكتبها المستخدم؛ PAT موثق على argv؛ سياسة non-root مخالفة للوثيقة؛ تعليمات Angular تهمل `npm ci`؛ launcher GUI يختلف عن المثبّت | خطر كود متغير في مسار امتيازي وتسرب PAT وتعليمات تشغيل مربكة/فاشلة | ثبت تحت `/opt` أو حزمة root-owned، استقبل PAT عبر getpass/stdin، وحّد سياسة الامتياز والـlauncher، ووثق Node و`npm ci` |

## نقاط القوة التي ينبغي الحفاظ عليها

- `utils/safe_exec.py` يرفض أوامر النص ويستخدم قائمة argv مع `shell=False` وtimeout في مسارات الفحص المباشرة؛ ومسار إزالة الملفات المميزة يستعمل `--` قبل المسار.
- `SystemReader` يمرر أوامر الماسحات كـargv إلى التنفيذ الآمن، ما يقلل حقن الأوامر خارج مسارات GUI/planner المعيبة.
- ماسح الأسرار يحجب القيمة المكتشفة في الـfinding بدلاً من طباعة السر كاملاً.
- توجد تأكيدات تفاعلية قبل بعض الأفعال المؤثرة (auto-fix، حجب IP، الحفظ/الرفع إلى GitHub)، ولا يوجد رفع تلقائي وفق المراجعة.
- الإعدادات تحاول ضبط `~/.ayfam` إلى 0700 و`config.json` إلى 0600 وتخفي الأسرار المعروفة في `Settings.all()`؛ يجب الإبقاء على هذه النية مع تصحيح symlink والكتابة الذرية.
- مسارات الفحص الرئيسية تجمع مستوى/اتجاه المخاطر وتعزل أخطاء الفحوص الفرعية كي لا يوقف خطأ واحد التدقيق كله.
- المفاتيح لا تُرسل من Angular مباشرة؛ API يعيد provider/answer فقط، ومساعد AI يعطي أولوية لمتغيرات البيئة ويستخدم HTTPS وtimeouts.
- الفصل التصميمي بين CTI العام والمطابقة المحلية، ووجود `LocalSnapshot` و`FakeSystem`، يتيحان اختبار المحركات دون المضيف الحقيقي عند استكمال الاختبارات.
- TypeScript يعمل بإعدادات strict؛ ونجح `npm run lint` وAngular compiler دون إصدار ملفات في النسخة التي راجعها المراجعون. كما أن Angular interpolation يستخدم العرض الآمن ولا توجد مؤشرات إلى `innerHTML` أو `bypassSecurityTrust` في النتائج.
- وجود `package-lock.json` يحسن قابلية إعادة إنتاج جانب Node مقارنة بجانب Python غير المقفل.

## خطة إصلاح واختبار عملية

### المرحلة 0 — إيقاف المسارات الخطرة (قبل أي نشر أو تشغيل root)

1. **عطّل توليد/تنفيذ سكربت المعالجة الحالي وزر Apply الرسومي** حتى وجود registry للإصلاحات. لا تشغّل `ayfam-remediation.sh` الناتج الحالي بحساب مميز.
2. **قيّد واجهة Angular إلى loopback** أو أوقفها؛ لا تستخدم `ng serve` خدمة شبكة. لا تسمح بأي وصول خارجي إلى `/api/assistant` قبل المصادقة وحدود المعدل.
3. **أصلح عقد CLI و`--check`** ثم نفذ smoke test لكل وضع قبل الإعلان عن الأداة.
4. **أصلح التثبيت النظيف**: أضف `pypdf` و`pytest` إلى المكان الصحيح، لا تثبت إلى Python النظام بـ`--ignore-installed`، وثبت بيئة مقفلة داخل venv.

### المرحلة 1 — اختبارات قبول للحواجز (يجب أن تكون محلية ومؤتمتة)

| الاختبار | معيار القبول |
|---|---|
| CLI entrypoint مع fake agent | `--cli` و`--scan` و`--harden` و`--cve` تستدعي API معرفة؛ `--check` يطبع `PreflightReport.text()`؛ رموز الخروج صحيحة ولا input غير مقصود في الأوضاع المباشرة |
| Remediation injection | finding يحمل `$(marker)` أو backticks أو اسم ملف باقتباس؛ لا ينفذ marker في التوليد أو dry-run أو التنفيذ؛ لا تُقبل إلا `fix_id` مسموحة وargv متحققة |
| GUI Apply | finding يبدأ بـ`sudo` ومسار فيه اقتباس؛ لا يحدث `subprocess.run(..., shell=True)`، ويُرفض/ينفذ فقط registry مسموح |
| تثبيت نظيف | في Ubuntu/Debian فيها Python بلا pip، يثبت `python3-pip` ثم venv والملف المقفل؛ ينجح import `pypdf` وpytest ويفشل الإعداد عند خطأ حقيقي |
| API exposure | لا يصل مضيف شبكة ثانٍ إلى `/api/assistant` افتراضياً؛ عند تمكين النشر، ترفض الطلبات غير الموثقة وتطبق rate/concurrency limits |
| Settings | ترفض symlink والمكونات غير المملوكة وJSON غير object؛ عند فشل dump يبقى الملف السابق سليماً؛ تتحقق من owner و0700/0600 |

### المرحلة 2 — صحة الفحوص وقرارات المعالجة

1. اختبر HardeningEngine بحالات `passwd/group=0664` و`shadow/gshadow=0660` وبالحالات السليمة `0644/0640`.
2. اختبر SecretScanner على مجلد فيه `id_rsa` و`.pem` و`.key` وملف كبير/ثنائي متخطى، مع تقرير حدود التغطية.
3. اختبر `authorized_keys` مع options مركبة و`command=` مخصص، وLogForensics مع `auth.log.1` الأقدم ثم النجاح في `auth.log` وعناوين IPv6.
4. استخدم نظاماً مزيفاً يضم `/usr/bin/find` ذا SUID وتحقق من ظهوره في deep audit و`SuidIntelligence`.
5. اختبر KEV الكامل: CVE قديم، تصادم product، إصدار متأثر وغير متأثر؛ لا يرتفع إلى critical دون مطابقة دقيقة.
6. اختبر سياسة URL ضد `127.0.0.1` و`::1` وRFC1918 و`169.254.169.254` وتحويل public إلى private، وتحقق من عدم تنفيذ `connect_ex` عند الرفض.
7. اختبر CTI عند timeout و`ValueError` من JSON ورفض googleSearch لنموذج 3 مع توافر 2.5؛ ارفض feed بلا sources/تاريخ/URL صالح أو لا يدعم IO C المدعى.
8. اختبر مستشار المعالجة بحيث لا يعرض سلسلة عالية المخاطر كـ`low`.

### المرحلة 3 — واجهة المستخدم والعقود

1. أضف `npm test`/Vitest أو Angular test وPlaywright، ثم اختبر SecurityStateService مع API mock في نجاح وفشل وtimeout؛ لا تتغير `fixed` أو `authorized` قبل تأكيد backend.
2. أضف اختبار E2E لمسح يعرض run ID ونتائج backend لا عداد `setInterval` محلياً، وحالة فشل واضحة.
3. أضف فحص CSS في CI يمنع `*_NN` ولقطات لحالات critical/high/fixed/USB-blocked.
4. اختبر Clipboard في secure context وPermissionDenied/HTTP، ولا تعرض رسالة نجاح قبل الحل الفعلي.
5. أضف اختبارات API handler للـhealth/OPTIONS، JSON object وغير object، lengths سلبية/فارغة/أكبر من 32768 وبطيئة، provider 200/401/429/timeout، ومنع تسرب الأسرار إلى logs.

### المرحلة 4 — بوابة CI والإصدار

- أمر Python واحد موثق: `python -m pytest -q --maxfail=1` في venv مقفل، مع coverage للـ`api_server` و`engine` و`tools` و`brain` و`core` وحد سطور/فروع متفق عليه.
- أمر Node: `npm ci && npm run lint && npm test && npm run build` مع إصدار Node معلن.
- لا شبكة أو وصول حقيقي للمضيف في الاختبارات الافتراضية؛ اجعلها mocks/adapters ثابتة. اختبارات live تحمل marker `live`/`manual` وتتطلب اختياراً صريحاً ومهلة قصيرة.
- اختبر ترتيب جمع pytest وتنفيذه المتوازي بعد إزالة HOME العالمي والـtmp الثابت، وتحقق أن لا HOME حقيقياً أو أثر مؤقتاً يبقى بعد الاستثناء.
- اختبر كل أمر في README/INSTALL مقابل `--help` ضمن CI أو ولّد قسم CLI من تعريف parser لمنع الانجراف.
- افحص lockfile في CI باستخدام `pip-audit` أو OSV، وأصدر المشغلات من مسار root-owned غير قابل للكتابة من المستخدم.

## المخاطر المتبقية بعد الإصلاح المقترح

- **التحقق من التغطية التشغيلية:** حتى بعد إصلاح المنطق، ستبقى بعض الفحوصات مقيّدة بصلاحيات المستخدم، السجلات المتاحة، ونوع التوزيعة. يجب وسم النتائج الجزئية صراحة بدلاً من إعلان نجاح كامل.
- **تضارب نماذج الثغرات وبيانات CTI:** تتغير قواعد KEV/CPE وواجهات المزودين؛ يلزم cache موقّع/موثق أو fresh feed، اختبارات fixtures تاريخية، وإظهار الثقة ومصدر الدليل للمشغّل.
- **المعالجة ذات الامتيازات:** حتى registry مسموح يحتاج مراجعة change-management، نسخاً احتياطياً مثبتاً، least privilege، وrollback/verification بعد كل إصلاح؛ لا يكفي منع حقن shell وحده.
- **الاعتماد على LLM/المزود السحابي:** لا يزيل consent/redaction الخطر كلياً؛ يجب أن يبقى المسار المحلي متاحاً، وأن تسجل metadata لا prompts/أسرار، وأن تكون تكلفة/حدود المعدل مرصودة.
- **نشر الواجهة:** `ng serve` ليس خادم إنتاج. يحتاج أي وصول متعدد المستخدمين إلى reverse proxy، TLS، مصادقة وتفويض، حماية CSRF/جلسات بحسب التصميم، مراقبة وحدود طلبات.
- **التبعيات والنظام المضيف:** lockfile يقلل الانجراف ولا يلغي CVEs أو اختلافات Python/Node/OS؛ يلزم تحديث دوري، SBOM/فحص CVE، وتجربة تثبيت على الصور المدعومة.

## معايير الإغلاق

لا تغلق أي نتيجة **blocker** أو **high** بمجرد تعديل ساكن. يلزم لكل واحدة: مراجعة code، اختبار انحدار حتمي يثبت حالة الاستغلال/الفشل السابقة، اختبار قبول للمسار الإصلاحي، وتشغيل CI النظيف. قبل الإصدار، يجب أن ينجح تثبيت جديد من ملفات مقفلة، واختبارات Python/Node، وفحص أوامر CLI الموثقة، واختبار عدم التعرض الشبكي الافتراضي للـAPI.
